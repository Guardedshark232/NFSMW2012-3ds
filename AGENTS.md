# AGENTS.md

Instructions for coding agents working in this repository.

## What this project is

A Nintendo 3DS port of *Need for Speed:
Most Wanted (2012)*, using devkitPro, libctru,
citro3d and citro2d. It renders extracted world geometry from the retail PC
game (RomFS assets), drives a car with a chase camera, and draws an EasyDrive
HUD on the bottom screen.

The playable world is a single extracted arena (`ARENA_527911.BNDL`) plus
hand-authored container-yard dressing. It is not the full game.

## Build

Requires devkitPro (`DEVKITPRO`, default `/opt/devkitpro`) with `3ds-dev`,
`citro3d`, `citro2d`, plus `tex3ds` and `picasso`.

```sh
make -j8     # nfs_3ds.3dsx (embeds romfs/ and regenerates the atlas texture)
make cia     # nfs_3ds.cia (makerom/bannertool run through wine)
make clean
```

`make cia` uses the `.wine` prefix and tools under `NFSU2-3DS/tools/3ds-bin/`.
Do not modify those unless the packaging step is actually broken.

## Source layout

- `src/core/` — entry point, asset loading, BNDL reader, tinf decompressor.
- `src/renderer/` — Citro3D world/car rendering, HUD, shader, diagnostic
  framebuffer dumps.
- `src/input/`, `src/physics/` — controls and vehicle simulation.
- `src/renderer/vshader.v.pica` — PICA vertex shader. `vshader.shbin` and
  `vshader_shbin.s` are generated by the Makefile; do not hand-edit them.
- `src/renderer/world_mesh.cpp` — dynamic spatial streaming engine (`world_manifest.bin` + `sec_*.mwmesh`), chunk upload/unloading, local ground-height grids. `MWVertex` here is the authoritative vertex layout.
- `tools/` — host-side Python asset pipeline (Pillow + numpy required).
- `romfs/assets/` — generated runtime assets. `world_manifest.bin`, `sectors/*.mwmesh`, and `*.t3x` are build products; regenerate them, never hand-edit.
- `progress` — use this file to summerise changes made

## World asset pipeline

The tools read the retail PC game from `MW_DIR`
(`.../Need for Speed(TM) Most Wanted/HAWAII`). Rebuilding world data is
impossible without that install.

```sh
python3 tools/world_textures.py         # material -> albedo map (JSON)
python3 tools/extract_world_sectors.py  # extract all 8 ARENAs + districts into spatial sectors + manifest
python3 tools/build_atlas.py            # atlas PNG alone, if only textures changed
python3 tools/yard_props.py             # placement preview against the current mesh
make -j8                                # compress atlas to .t3x and re-embed RomFS into .3dsx
make cia                                # build installable .cia
```

`tools/extract_world_sectors.py` is the full open-world sector builder. It processes all 8 `ARENA_*.BNDL` files plus connecting districts, dedupes LOD copies, partitions into 500m sectors, applies container yard dressing to the harbour, and writes `romfs/assets/sectors/` and `romfs/assets/world_manifest.bin`.

`tools/extract_world.py` is the single-arena reference extractor for `fairhaven_block.mwmesh`.

`tools/yard_props.py` procedurally dresses the empty container terminal with
stacked containers and gantry beams. It is wired into `extract_world.py` through
`make_yard_decorator`; placement is hand-authored because the original game
streams those props and their transforms are not in the extracted arena.

## Coordinate spaces

- Bundle/world coordinates come straight from the game files.
- Mesh-local coordinates = world − `(-168.0, 30.0, 4058.0)` (the arena origin).
- The renderer, physics and `yard_props.py` work in mesh-local space.
- `collect_world_chunks` carries world-space parts; `build_indexed_chunk`
  subtracts the origin. The yard decorator converts world → local → world
  around `yard_props.build_parts`. Getting this wrong shifts props by ~4 km.

The reference yard is around mesh-local `(-176, -139)`; the quay deck is
roughly `y = -14.5 .. -8.5` there.

## `.mwmesh` v3 format

Written by `tools/extract_world.py:write_mwmesh`, read by
`src/renderer/world_mesh.cpp`. (The module docstring at the top of
`extract_world.py` still describes the old v1 layout — trust `write_mwmesh`
and `MWVertex`, not that docstring.)

- Header: `<4sIII` = `MWMS`, version `3`, chunk count, reserved.
- Chunk header: `<II6f2I` = numVerts, numIndices, bboxMin, bboxMax, two zeros.
- Vertex: `<3f4B2h` = float32 x, y, z; uint8 r, g, b, a; int16 u, v (20 bytes).
- Indices: uint16, padded to an even count.
- UVs are pre-baked into the world atlas and stored signed-16 biased by
  −32768. The shader decodes `s / 65535 + 32768 / 65535`.
- The colour channel is a neutral lighting tint baked by `shade_color()`, not
  a material colour. A part may carry an optional `color` tuple that biases
  this tint (used by `yard_props.py`).

Keep `MWVertex` at 20 bytes; the `static_assert` in `world_mesh.cpp` enforces
it. `BufInfo_Add(info, data, stride, 3, 0x210)` is required for the three
attributes.

## Texture atlas

- One 1024×1024 RGBA4444 atlas, 32×32 tiles, 32×32 grid.
- Tile (0,0) is reserved grey fallback, leaving 1,023 texture slots. The
  smaller tiles let the full-world material set fit in the 3DS texture limit.
- Each tile has a 1-texel inset; wrapping is `CLAMP_TO_EDGE`, so source UVs
  outside `[0,1]` cannot be repeated. `fit_part_uvs()` fits each part's UV
  range into its tile, which makes very large tiled surfaces look soft.
- `build_atlas.uv_remap()` mirrors V because `tex3ds` flips rows when packing.
- Materials are mapped to tile origins in `tools/world_texture_map.json`; the
  extractor bakes the rectangle into the mesh. Editing the map alone requires
  re-running `extract_world.py`, not just `make`.

## Rendering invariants and known pitfalls

- Re-fetch the buffer info with `C3D_GetBufInfo()` for every chunk draw.
  Holding one `C3D_BufInfo*` across draws leaves the first VBO bound and
  produces giant-slab artifacts.
- `C3D_GetTexEnv()` marks the TEV stage dirty; the inline
  `C3D_TexEnvSrc/Func` setters do not. After the sky draw, the world's texture
  combine must be re-flagged with `C3D_DirtyTexEnv(env)` or the map renders
  untextured.
- Reversed-Z depth (`C3D_DepthMap(true, -1.0f, 0.0f)`) is re-applied every
  frame because citro2d changes the depth mapping.
- The CPU-side ground grid in `world_mesh.cpp` keeps the car and camera on
  the nearest surface. When adding geometry, check that it does not create
  spurious high cells under the car.
- `MAX_TRI_EDGE = 100.0` drops geometry triangles with any edge > 100 m as a
  decoder-artifact guard. Long beams must be split into ≤40 m spans (see
  `yard_props._beam`).
- PICA attributes arrive unnormalised as integers. Constants cannot be
  source operands of `mul`/`add` in Picasso; load them into a register first.
  Only `GPU_BYTE`, `GPU_UNSIGNED_BYTE`, `GPU_SHORT` and `GPU_FLOAT` exist.

## Diagnostics

Both are compiled out by default and must stay off for release builds.

- `src/renderer/fbdump.cpp`: set `FB_DUMP_ENABLE 1` to write
  `sdmc:/fbraw_top_<frame>.bin` and `fbraw_bottom_<frame>.bin` at frames
  60/300/540/780/900. Top is 240×400, bottom 240×320, tiled/Morton ABGR.
  A host decoder is required; none is checked in.
- `src/core/main.cpp`: `#define DIAG_AUTO_DRIVE 1` holds throttle and logs
  `sdmc:/drive_diag.txt` (`f <frame> spd ... pos ... gnd ...`). Useful for
  reproducing a specific location by frame number; frame 540 is the yard.

When capturing emulator output, remove old `fbraw_*` files first so stale
frames are not mistaken for the new run.

## Testing expectations

- Always build at least `make -j8` after changing `src/`; check that it links
  and that the RomFS is re-embedded.
- After changing any world/texture tool, run the full pipeline and confirm the
  mesh size and chunk count in the extractor output are sane.
- Runtime smoke test: launch the `.3dsx` in Azahar or on hardware, confirm
  textures load, spawn FPS is ~60, and the car stays above the ground. The
  previously verified numbers are ~62 FPS at spawn and ~59 FPS driving.
- World coordinate changes should be checked against the top-down preview
  (`/tmp/opencode/mw/fairhaven_preview.png`) and the yard placement preview.

## Known limitations

- Container stacks and gantry cranes are procedural and hand-placed; the
  original instanced prop transforms are not decoded.
- The real Porsche BNDL mesh is not decoded; the car is procedural geometry.
- Only `ARENA_527911.BNDL` is extracted (radius 750 m, clipped to 650 m).
  Streamed `TRK_UNIT*` set-pieces are absent. 
- Per-part UV fitting sacrifices tiling detail on large surfaces.
- `nfs_3ds.3dsx`, `nfs_3ds.cia`, `*.mwmesh` and `*.t3x` are generated
  artifacts; do not treat diffs in them as source changes.

## Style

- Keep C++14, `-fno-rtti -fno-exceptions` compatibility and the existing
  module layout (`core`/`renderer`/`input`/`physics`).
- GPU memory comes from `linearAlloc`; keep per-frame allocations out of the
  render loop and preserve the packed vertex sizes.
- Python tools are plain scripts run from the repo root with `python3`; keep
  them dependency-light (stdlib, Pillow, numpy) and print a short summary of
  what they wrote.
- Match the surrounding naming and comment density. Comments should explain
  hardware/game-format quirks, not restate the code.
